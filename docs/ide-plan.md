## 用户已明确的方向

1. altaed 与 rmj.ac 关系不大，可以借鉴任务与实现方式，不绑定其云端、后端部署或网页版前端。
2. 敏捷开发，首先做一个 IDE；设计通用机制，允许开发者编写远程提交插件。
3. 文件可以不关联题目，或至多关联一道题；同题可以有多个文件或解法版本，IDE 不限制文件命名。不保存也能编译，题目信息用于编译／提交。
4. editor 是可独立的组成部分，既可作为组件引用，也可集成。交付 IDE 是主要目标。
5. 本地测试参考 CP Editor；也可以编译生成程序，直接进行终端交互。
6. 首轮通过浏览器 Competitive Companion 一键导入题目信息和样例，导入的信息需要持久化。用户已澄清入口；CPH 本地 `.prob` 文件兼容不属于当前已确认范围。
7. 绑定题目只为代码文档继承题目信息；每份代码有自己的本地信息。新增或修改测试不会改变原始题目信息（包括本地保留的原始记录），也不会传播到绑定同题的其他代码。
8. 普通源码与附属信息分离，整目录可携带全部信息，单独复制源码只带源码，另提供导出代码与测试的操作。改名保留身份，另存为复制当前题目信息、测试和配置，形成独立文档。
9. 退出 IDE 自动保存恢复草稿；关闭有未保存内容的标签时，可以保存、保留草稿或丢弃。草稿包含源码、题目信息和测试。
10. Companion 每次导入创建新的本地题目实例，不复用原来的题目。解绑保留代码和测试、移除提交目标；改绑允许保留旧用例、添加新样例或替换测试。
11. 首版主要支持 C++ 编译，可以暂不内置 g++；后续 Windows 部署需要内嵌 MinGW-w64 工具链。
12. 内置多个 checker，包括浮点比较。交互运行可以打开新终端，死循环由用户自行 break；再次运行不自动终止旧终端中的程序。
13. 首个提交平台是 Codeforces，可以通过内嵌浏览器或连接本地 Chrome 实现；实现路线尚需验证。
14. 加密网络中继与云端托管 CF 会话代提交两种方式都需要，分阶段实现。它们是可选的提交通道，本地 IDE 和直接提交独立可用。

原型已经通过用户对代码编辑与虚拟 LSP 的手动验收。完整 SDK 依赖隔离、真实 LSP、编译运行和远程提交均不能由这次验收推定已完成。

## 建议的最小对象与职责

文件与题目的数量关系、每份代码独立拥有本地信息的语义已经确定。以下对象划分和具体落盘方式是工程提案。

| 对象 | 职责 |
| --- | --- |
| 代码文档 | 当前源码、内容版本、语言、可选磁盘路径，以及本份代码独立拥有的题目信息、测试与本地配置 |
| 文档的题目信息 | 可选；绑定时继承的来源、原始链接或标识、标题、限制与输入输出约定；提交适配器可进一步解析平台目标 |
| 文档的测试用例 | 从题目继承的样例和手工添加的用例，包含输入、可选预期输出和来源；修改只作用于所属代码文档，未绑定题目也能使用 |
| 执行快照 | 点击编译／运行／提交时取得的不可变源码和对应版本、配置、运行方式、题目目标；样例运行同时固定用例内容 |
| 本地工具链 | 编译器、解释器、启动参数与本地语言配置 |
| 远程提交作业 | 使用哪个快照、目标平台与语言，以及远程编号和结果状态 |

例如 `brute.cpp`、`fast.cpp` 和 `retry.py` 都可以关联同一道题；不根据文件名推断或强制绑定题目。“多个版本”先支持多份文件，不据此增加内置版本管理系统。

绑定同题后，各文档可以从相同题目信息开始，但本地状态独立。例如给 `brute.cpp` 添加反例或修改继承的样例，`fast.cpp` 的测试保持原状，本地保留的原始题目信息也不改变。持久化以代码文档为归属单位，不能用题目 URL 或平台题号作为多份代码共用的可变状态键。这里确定的是数据归属与修改隔离；物理复制方式和后续主动更新策略仍待设计。

文档使用独立标识，磁盘路径是可选属性。IDE 内改名保留身份与关联；另存为创建独立文档，初始复制当前题目信息、测试和本地配置，此后互不影响。整目录迁移需恢复关联；外部单独移动源码不承诺携带附属信息。具体存储定位方式仍需设计。

题目关联由 IDE 管理，不进入通用 Editor 核心。可以借鉴 rmj.ac 的类型化标识与事务边界，但不预设引入其 Graph、数据库、Redis 或服务端模型。

## 未保存代码的编译与提交

建议流程：当前文档 → 捕获内容与配置快照 → 本地运行器或远程插件 → 结果绑定该快照。

- 本地编译器需要文件时，在临时目录物化快照；不要求用户选择保存路径，不覆盖已有源码文件。
- 只编译时保留可定位的编译产物，并允许后续运行或导出；临时产物的清理不能妨碍正在运行的程序。
- 每次执行拥有独立的产物与源码版本标识；新编译不覆盖旧终端正在执行的文件。编译失败不自动运行旧产物。
- 提交插件接收源码快照，即使文档没有磁盘路径也能工作。
- 执行期间可以继续编辑；结果说明对应哪个内容版本，避免将旧代码的结果显示为新代码的结果。
- 文件保存、编译运行和远程提交是独立动作。具体快捷键与默认行为另行设计。
- 本地 C++ 工具链选项与平台的远程编译器／语言编号分开描述，由插件完成平台映射。
- 题目首先提供题目标识、样例、限制和支持语言等上下文；是否允许题目声明特殊编译参数，需要单独决定。

退出应用时自动保存会话草稿，重启后恢复源码、题目信息与测试。关闭有未保存内容的标签时提供保存、保留草稿或丢弃；主动丢弃的内容不能在重启时重新出现。恢复草稿不覆盖用户磁盘源码。落盘时机、崩溃恢复与磁盘内容冲突处理属于后续实现细节。

## C++ 工具链与 Windows 部署

首版使用已有外部 C++ 编译器，允许发现和手动指定编译器路径。C++ 标准、编译参数提供配置入口，默认值尚未确定。工具链配置要区分编译器类型、路径、参数和环境，避免把 `g++` 命令名或系统 PATH 写死。

建议支持本地头文件、可选工作目录及编译产物导出；保存代码的本地依赖应按其逻辑目录解析，未命名代码允许选择工作目录。这些具体行为尚属工程提案。

Windows 内嵌工具链是后续部署要求。MinGW-w64 提供 Windows 头文件和库，完整发行还需要 GCC、链接器等组件；官方列出了可独立部署的预编译工具链。应通过同一工具链接口加载应用附带目录，同时保留外部编译器选择。发行来源、固定版本、运行库、升级及发布包材料在 Windows 阶段验证，不在当前选择具体版本。[官方说明](https://www.mingw-w64.org/downloads/)

## 本地测试与交互运行

CP Editor 的官方介绍明确支持未保存代码运行、多组测试与预期输出比对；其文档也提供测试数据保存和题目 URL 恢复能力。altaed 借鉴这个工作流，具体交互由用户测试决定。参考：[产品介绍](https://cpeditor.org/)、[保存与题目关联](https://cpeditor.org/docs/preferences/actions/)。

建议同一文档提供三个操作，使用同一套源码快照与工具链机制。每次新执行捕获当前内容；若选择运行已有产物，应明确其对应的源码版本：

| 操作 | 行为 |
| --- | --- |
| 只编译 | 展示编译诊断并生成可执行产物 |
| 运行测试 | 一次编译后运行单个或选中的多个用例，展示输入、预期输出、实际输出、差异和运行状态 |
| 交互运行 | 为本次执行打开新终端，用户分次输入、实时查看输出并自行中断；已有终端中的程序继续运行 |

测试用例可以手工添加、修改和删除。按用户 2026-11-03 的最新决定，预期输出为空（包括空文件）时只运行和观察，有内容时自动比较，不再显示逐例比较复选框。结果至少区分编译失败、运行失败、超时、取消和正常结束；只有配置了输出比较规则才能给出本地通过／不通过。

内置 checker 已确定。建议首组为严格文本、按空白分隔的 token 比较，以及浮点数比较；checker 类型和参数属于每份代码的本地配置。浮点 checker 支持绝对／相对容差，具体公式与默认阈值需明确，不能简单给所有数字使用固定小数位。实现检查应覆盖接近零、极大值、科学计数法、token 数量不符以及 NaN/Infinity 等特殊值；非浮点 token 不应被宽松接受。用户可用边界样例评判比较行为。

交互运行采用独立终端会话，可以由系统终端启动器承接，具体终端集成方式待验证；用户通过 Ctrl-C 等终端操作中断程序，不因再次运行而自动结束旧会话，也不套用样例测试的短超时。终端关闭、应用退出与临时产物清理的行为需要在原型中验证。批量测试使用固定输入与输出捕获，仍提供每例超时与取消。自动交互题的 interactor 支持需要单独规划；导入的 `interactive` 标记应保存，不能将普通样例运行当成交互题评测。

运行中的输出、诊断和状态属于具体执行；继续编辑源码或测试数据时，不将旧结果标为新版本的结果。进程生命周期和取消处理属于本地运行器，不进入 Editor 核心。

## 题目导入与保存

已确认入口是 Competitive Companion。其官方协议通过本地 HTTP 接收 JSON，提供题名、分组、URL、样例、时间／内存限制、交互标记、输入输出类型及部分语言信息；按来源实际提供的内容保存，不假定含有完整题面或平台提交语言列表。参考：[官方协议](https://github.com/jmerle/competitive-companion#custom-tools)。

导入规则：接收并校验数据后，每次创建新的本地题目实例。建议同时打开新的未命名代码文档并继承信息与样例，再按文档保存；新标签的具体交互由原型验证。来源 URL 可以相同，但不能作为复用旧题目的去重键。创建本地题目实例不要求用户立即保存磁盘源码。导入适配器和远程提交插件分别工作；本地导入与测试不依赖安装提交插件。

- 源码保持普通文件，关联与元数据单独存储，整个目录可携带完整信息，单独复制源码只带源码；另提供代码与测试的导出操作。目录内 `.altaed/` 元数据和未命名文档的会话存储是实现提案，具体布局与导出格式尚未决定。
- 按代码文档保存题目来源、来源标识／链接、已获取的信息、继承的样例、本地新增用例与本地配置；重新打开或重启后能够恢复各自的状态。元数据修改也会触发持久化，不能只依赖源码发生变化。
- 同题代码的本地信息互相独立；编辑继承的样例、添加或删除用例，只影响当前文档。原始导入信息与后续本地修改建议保留来源区分，不能将本地修改回写为其他文档继承的题目信息。
- 重复导入同一来源仍然新建，不改变原文档或原题目实例。主动刷新旧文档是独立操作，不属于浏览器导入的隐含行为；是否需要该操作可以后置。
- 解绑保留源码与测试、移除提交目标。改绑先展示新题信息，用户可以保留旧用例、添加新样例或替换测试；操作只影响当前文档，具体选择界面与来源标记再设计。
- 协议声明的文件输入输出或交互题模式需要保存；运行器尚不支持的模式要明确显示。成功导入与支持该题目的运行模式是两项能力。
- 元数据保存需要版本字段与原子写入；导入数据和源码编译命令分开，导入本身不自动执行程序。

CPH 的 `.prob` 是另一种本地 JSON 数据入口，当前仅作为兼容性参考，不排入首轮。其元数据保存实现和字段定义已核实：[保存实现](https://github.com/agrawal-d/cph/blob/main/src/parser.ts)、[数据类型](https://github.com/agrawal-d/cph/blob/main/src/types.ts)。

## 插件的最小提案

首个平台已确定为 Codeforces。接口先围绕一次真实提交设计，不提前建设插件市场。候选操作：

| 操作 | 用途 |
| --- | --- |
| `resolveProblem`（可选） | 将链接或平台标识转换为题目关联及可提供的信息 |
| `listLanguages` | 返回目标支持的远程语言／编译器选项 |
| `submit` | 提交指定源码快照，返回可追踪的提交标识 |
| `getSubmissionStatus` | 获取排队、编译、运行、结束或失败状态 |

IDE 负责文档、任务展示与用户操作；插件适配平台认证、参数映射和远程请求。题目元数据不携带账号密钥。

先用测试适配器验证契约，再让一个 IDE 外部编写的最小插件完成真实提交，以验证“允许编写插件”确实成立。测试适配器不作为远程链路完成的证据。

插件运行方式尚未决定。可考虑外部进程交换结构化消息，以便不同语言编写；运行方式与协议需要通过 CF 真实链路验证。接口描述应注明协议版本、错误与未知状态，不能把无法确认的提交自动当作失败并重发。

## Codeforces 浏览器提交与分阶段中继

已核实：CF 当前公开 API 方法列表未提供提交代码接口，`user.status`、`contest.status` 等可查询提交记录。因此浏览器提交链路需要独立验证，不能只实现公开 API 调用就宣称完成提交。[CF 方法列表](https://codeforces.com/apiHelp/methods?locale=en)

建议首轮采用本机 Chrome 扩展加本地 Rust 桥接：altaed → 本地桥接 → 扩展 service worker → CF 提交页面。扩展通过 content script 操作页面表单，使用该浏览器中的 CF 会话；登录或站点验证在浏览器完成。Native Messaging 需要注册本地 host，由 Chrome 启动并与扩展通信；现有 altaed 进程再与该 host 连接。此路线无需将 Cookie 提取进源码元数据。[Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)、[Content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)

内嵌 Chromium/CEF 保留为另一种浏览器实现。它涉及浏览器多进程、GPUI 原生窗口／渲染集成和独立会话存储；不等于直接嵌入现有 Chrome 标签页，不能假定继承现有 Chrome 登录状态。[CEF 官方集成说明](https://github.com/chromiumembedded/cef/blob/master/docs/general_usage.md)

用户已选择两类中继分阶段实现，建议顺序如下：

| 阶段 | 行为 | CF 会话位置 |
| --- | --- | --- |
| 直接提交 | 本地浏览器完成 CF 提交 | 本地浏览器 |
| 加密网络中继 | 浏览器经中继访问 CF，保留浏览器到 CF 的 HTTPS；不进行 TLS 解密 | 本地浏览器 |
| 云端代提交 | 云端接收源码快照、题目和语言，使用云端托管的会话执行提交并返回任务状态 | 按用户隔离的云端会话 |

两种中继是可选能力，用户可使用直接通道。网络中继作为浏览器传输层选项；云端代提交作为任务执行后端，二者不能仅用一个“代理 URL”字段混为一谈。Chrome 的 proxy API 支持按 PAC 等规则配置代理，但需要 `proxy` 权限，也要处理与用户已有代理的冲突；具体接入方案先做验证，不自动覆盖用户配置。[Chrome proxy API](https://developer.chrome.com/docs/extensions/reference/api/proxy)

云端代提交需要独立的账号连接与会话生命周期，不能假定本地 Chrome 的会话可直接迁移。源码只按本次提交快照上传，题目元数据与导出包不携带账号密钥。云端任务编号和 CF submission ID 分开记录：服务器收到了任务，不代表 CF 已接收提交。

所有通道都需要记录请求标识、源码版本／摘要、账号、目标、语言与发送状态。收到明确 CF submission ID 才建立关联；不能直接将账号最新一条提交认作本次请求。发送后断线或超时应进入“结果未知”，先核实已有记录，不自动重发或切换通道再提交。云端请求幂等只能防止重复创建本服务任务，不能据此宣称 CF 提交具有恰好一次保证。

真实验证包括账号连接、填写语言和代码、提交 ID 关联、状态查询、登录过期、站点验证，以及直接／中继路径的成功率和耗时。更快和更稳定是中继的目标，需要在目标地区网络下测量；目前未完成真实 CF 提交或中继服务验证。中继服务的节点、部署、账号托管方式和成本另行设计，不要求复用 rmj.ac 后端。

## 建议的敏捷交付顺序

每次迭代只交付一个可操作的增量，用户亲自评判体验，工程检查负责行为回归。

| 迭代 | 可交付增量 | 用户可以实际完成的事 |
| --- | --- | --- |
| 1 | 基本 IDE：文件、分离元数据、另存为与草稿恢复 | 改名保留信息，另存为得到独立副本，退出恢复或主动丢弃 |
| 2a | C++ 本地运行器：外部编译器、未保存编译、产物与新终端 | 不保存就编译运行，多终端互不替换，用户自行中断 |
| 2b | 本地用例测试：单例／多例、内置 checker 与浮点容差 | 同一份代码跑样例，检查文本和浮点结果 |
| 3a | Companion 导入、题目关联与持久化 | 每次导入新建，同题代码各自保存信息，支持解绑和改绑 |
| 3b | 插件契约与 CF 浏览器桥接验证 | 将当前文档的题目和语言传入浏览器提交页面 |
| 4 | CF 真实提交插件 | 提交当前源码快照并关联真实 submission ID 与结果 |
| 5a | 可选加密网络中继 | 保留本地 CF 会话，经中继访问 CF 并完成提交 |
| 5b | 可选云端代提交 | 连接云端账号会话，上传提交任务并追踪云端任务和 CF 结果 |
| 后续 | Windows 内嵌 MinGW-w64、第二插件与 Editor 解耦验证 | 无预装编译器的 Windows 环境可编译，验证插件和组件复用 |

语言方向、首个平台和文档保存语义已确定；实现工作量与真实外部链路尚未验证，因此此处不承诺日期。真实 C++ LSP 是基本 IDE 的独立增量，可以与本地运行器并行推进；目前的模拟 provider 不算真实语言服务完成。不要求一轮完成表格中所有细节。

建议下一次用户验收串起以下动作，最终通过标准由用户决定：新建任意名称的代码或未命名文档 → 不保存就交互运行 → 从 Companion 导入题目并跑样例 → 第二份任意命名的代码绑定同题 → 修改其中一份的样例并添加反例，另一份保持原状 → 重开后各自的绑定、测试与配置仍然独立。每个动作可以拆成独立的小版本，依次交给用户测试。

Editor 解耦贯穿迭代：优先明确文档、视图、事件与 provider 的调用边界，避免 IDE 业务继续渗入核心；可以先随应用构建，不把完成全部物理拆包作为每轮前置。独立 SDK 是否另行发行，是未来的产品决定。

## 开始编码的条件与工程约束

产品层面已无阻塞首轮编码的问题。用户要求可扩展、命名规范、人类可读，避免把临时假设硬编码为正式行为。具体约束记录在仓库 [AGENTS.md](../AGENTS.md)。剩余技术选择由实现者依据现有代码与小原型收敛，不要求用户逐一选择库、接口名称或内部格式。

已检查现有 Rust 原型：`EditorLab` 将 Buffer、视图、路径和保存状态集中在窗口对象中；启动流程固定加载 `scratch/main.cpp`，显示固定的双视图标签并安装模拟 C++ provider。这些用于保留实验基线，正式代码需要逐项隔离。文本模型实验复用了 Zed 的原始文本能力，正式宿主继续复用这些能力，不另造一套编辑内核。

首个正式增量建议先用一个应用 crate 的五个模块：

| 模块 | 职责 |
| --- | --- |
| `document` | `DocumentId`、每份代码的附属信息、修改状态与快照契约 |
| `session` | 打开的文档、视图关联、当前文档与恢复状态 |
| `storage` | 普通源码、版本化元数据、草稿的读写和错误恢复 |
| `editor_adapter` | Zed 编辑模型／视图初始化、编辑事件与 provider 接入 |
| `app` | 窗口、命令与用户操作的协调，不直接承载存储或进程实现 |

后续按需增加 `toolchain`、`terminal`、`checker`、`submission` 等模块；存在真实替换需求时才定义接口。编译器来自外部还是 Windows 内嵌目录、终端属于哪个平台、提交是本地浏览器还是云端，都不应改变文档核心。新增 checker 应主要修改 checker 模块和注册配置，新增提交平台应主要修改对应适配器。

配置首先覆盖真正会变化的路径、命令参数、超时、误差容限、端点和语言映射；稳定默认值具名集中，不追求“零常量”。先借鉴 rmj.ac Graph 中类型化标识、版本化数据和存储失败显式返回的实践，存储依然服务于 altaed 当前文档模型。

首轮任务按以下粒度实现，每项完成后有可运行结果或明确行为证据：

1. 建立正式宿主与文档身份，支持未命名文档、打开已有源码及动态标签，保留已验证的真实 Editor 编辑行为。
2. 实现源码与附属信息存储、改名及另存为；验证两个副本的本地信息互不影响，保存失败不会冒充成功。
3. 实现恢复草稿和关闭选择；验证退出恢复、主动丢弃、元数据单独修改以及写入中断后的恢复。
4. 接入真实 C++ 语言服务；与后续外部编译器、未保存内容编译和独立终端增量分别验证。

没有相关功能前不预建云端任务系统或完整插件运行时。浏览器提交和中继的外部未知不阻塞上述首轮任务；到对应阶段通过真实链路验证。每次交付报告改动、必要检查与限制，由用户决定体验是否通过。

## 后续随实现收敛的细节

1. 实现细节：元数据与导出格式、默认 C++ 标准和参数、checker 默认值、终端关闭与 IDE 退出后的进程处理，由小原型验证后收敛。
2. 浏览器插件体验：安装、账号连接、语言选择和站点验证，通过 CF 端到端原型让用户亲自验收。
3. 中继部署：网络中继接入、云端会话管理、节点与费用，在对应阶段设计；两类中继的需求已确定。
4. 题目元数据范围：导入数据之外，是否还需要平台特殊编译要求，可以结合 CF 插件实际需要决定。

当前已足够划分首轮实现任务，不必继续要求用户一次回答所有技术细节。后续按原型反馈细化；完整制题、团队、代码云同步与网页版功能不属于当前 IDE 的前置条件，可选提交中继按上述独立阶段推进。
